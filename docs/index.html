Endpoint privacy for AI

Your machine talks to AI.
Shadow makes sure it does so under a different name.

Shadow is a small background service between your machine and AI clouds. It replaces sensitive values in outbound requests with realistic, consistent fakes from a persistent persona. When the response comes back, including token-by-token streams, it puts the real values back. Your tools never notice. The provider never sees the real values.

Translate, don't block

The fakes keep their formats: emails, IBANs that pass mod-97, cards that pass Luhn. The model still gives useful answers.

Stays on the endpoint

The mapping lives in a ChaCha20-Poly1305 encrypted vault on your disk. No cloud, no account, no telemetry.

Every tool, every OS

Works as an HTTPS proxy or a base-URL gateway, on macOS, Linux and Windows. Non-AI traffic is never decrypted.

Concepts

Shadow has five moving parts. The library shadow-core implements all of them. The proxy and the CLI are thin layers on top.

Persona

A persona is the fake identity your machine presents. It has a company and domain, country, city, timezone and locale, a primary person, colleagues, a username, a user id and a hostname. It is generated once and saved to persona.json. By default the region is chosen far from the real one: a machine in Europe might become a company in Hangzhou, Osaka or Curitiba. Your first organisation name maps to the persona company. Your OS user, hostname and git identity map to the persona's own.

$ shadow identity

  person      Hui Zhao <hui.zhao@zhilan.cn>
  location    Shenzhen, China · Asia/Shanghai · zh-CN
  user id     user-b1f9a96f7997
  hostname    zhilan-dev-78

Vault

The vault is the real ↔ fake mapping. One real value always gets the same fake, and no two reals share a fake, so reversal is unambiguous. It is stored as vault.bin (SHV1 ‖ nonce ‖ ChaCha20-Poly1305(JSON)), and the 32-byte key is in vault.key, created with mode 0600. Writes are atomic (temp file + rename). Processes that share a data dir merge each other's entries before every save. Once a value has been seen, it is protected everywhere, even where no detector would match it.

The optional model detector calls a local NER sidecar on loopback (ml/: a small PyTorch BiLSTM + char-CNN tagger). It catches names and organisations that aren't in your dictionary. If the sidecar is down, Shadow carries on without it.

Translation

Findings from all detectors are merged: longest wins, then kind priority. Each one is replaced with its vault fake. In JSON bodies every string leaf is translated, but protocol fields are left alone: model, role, type, id, tool_call_id, data: URIs and similar. Identifying fields are overwritten with the persona: OpenAI user / safety_identifier and Anthropic metadata.user_id. Identifying headers are stripped or rewritten as configured.

Streaming

LLMs stream text in tiny JSON events, so a fake can arrive split: "Wei" in one event and " Zhang" in the next. Shadow parses SSE and NDJSON event by event. Delta fields of each format (OpenAI Chat and Responses, Anthropic, Gemini, Cohere, Ollama-style) go through a per-channel StreamUnmasker. It holds back at most longest-fake − 1 bytes, which guarantees the output equals unmasking the whole text at once. The held-back tail is flushed into the event that ends the block. When that event carries no text, it goes into a synthesized copy of the channel's last event.

Architecture

The workspace has three crates: shadow-core (detection, persona, vault, translation), shadow-proxy (rcgen CA, rustls MITM for AI hosts, blind tunnels, gateway, SSE translation; tokio + hyper 1.x) and shadow-cli (the shadow binary). Upstream calls use reqwest with rustls. Gzip and brotli responses are decoded transparently. An optional upstream_proxy (HTTP CONNECT or SOCKS5) carries intercepted AI traffic out through a relay.

Quick start

About sixty seconds from install to your first masked request.

shadow init --org "Acme GmbH"
echo "Mail jane@acme.com re Acme GmbH, card 4111 1111 1111 1111" | shadow mask
# Mail hui.chen@zhilan.cn re Zhilan Technology Co., Ltd., card 4837 2191 9471 3480

shadow run &
curl http://127.0.0.1:8877/gw/openai/v1/chat/completions \
  -H "Authorization: Bearer $OPENAI_API_KEY" -H "Content-Type: application/json" \
  -d '{"model":"gpt-4o-mini","messages":[{"role":"user","content":"Write a haiku for jane@acme.com"}]}'

Configuration

Shadow reads <data dir>/shadow.toml, and every key is optional. The data dir is $SHADOW_HOME, else ~/Library/Application Support/shadow on macOS, ~/.local/share/shadow on Linux, or %APPDATA%\shadow on Windows.

organization = ["Acme GmbH"]                 # first ↔ persona company; "Acme" protected too
terms = ["Project Falcon", "person:Jane Doe", "org:Globex"]
internal_domains = ["acme.com", "acme.internal"]
allow_domains = []                          # extra public domains never masked
allow_terms = []                            # values never masked

[persona]
region = "auto"                             # CN JP KR BR US DE IN AU MX ZA CA
# company = "…"   domain = "…"

[detectors]                                 # all true by default
email = true
phone = true
# person address iban credit_card national_id ip mac hostname secret path
local_facts = true                          # OS user, hostname, git identity, local domain

[model_detector]
enabled = false
url = "http://127.0.0.1:8878/detect"        # loopback only
timeout_ms = 300
min_score = 0.6

[proxy]
listen = "127.0.0.1:8877"
extra_hosts = ["llm.internal.acme.com"]     # glob * allowed
bypass_hosts = []
upstream_proxy = "socks5h://relay.example.net:1080"
strip_headers = ["openai-organization", "x-forwarded-for", "x-stainless-os"]

[proxy.persona_headers]
"x-request-origin" = "{hostname}"          # {user_id} {hostname} {company} {domain} {username}

[proxy.routes]
azure = "https://my-resource.openai.azure.com"

OS proxy mode covers tools that don't let you change the base URL. Set HTTPS_PROXY=http://127.0.0.1:8877 and trust the CA. Embedding the library

shadow-core is a plain synchronous library: Send + Sync, cheap to clone, with no async runtime required.

use shadow_core::{Shadow, ShadowConfig};

let shadow = Shadow::open(
    ShadowConfig::from_dir("/var/lib/myapp/shadow").with_terms(vec!["Acme GmbH".into()]),
)?;
let m = shadow.mask("Ping jane@acme.com about Acme GmbH");   // Masked { text, replacements, kinds }
let reply = shadow.unmask(&call_llm(&m.text)?);

let mut body = serde_json::json!({"model": "gpt-4o", "messages": [{"role": "user", "content": "…"}]});
shadow.mask_json(&mut body);             // skips model / role / type …
shadow.scrub_identifiers(&mut body);     // user, metadata.user_id → persona

let mut s = shadow.stream_unmasker();     // fakes split across chunks are restored
let out = s.push("Hi Wei Zh") + &s.push("ang!") + &s.finish();

Security model

Shadow protects the content of AI requests from the provider, from anyone the provider shares data with, and from logs, training sets and breaches downstream of it. The endpoint itself is trusted.

Source IP is not hidden by translation. Providers still see your egress IP and your API account. Use upstream_proxy to route intercepted AI traffic through a relay, for example one in the persona's region.
  • Local-only secrets. vault.key and ca/ca.key are created with mode 0600. Each vault save is encrypted with a fresh nonce and written atomically. Full-disk encryption is recommended.
  • Narrow interception. Only hosts on the AI list are decrypted. Everything else goes through a byte-for-byte TCP tunnel, and the PAC file sends only AI hosts to Shadow at all.
  • Loopback by default. The proxy binds 127.0.0.1, and Shadow warns if you bind a public interface. The model sidecar must be on loopback.
  • Best-effort detection. Regex, checksum and dictionary detectors can miss things. Add terms, enable the model detector, and run shadow scan on representative data.
  • Not scanned: images, audio, PDFs and other binary or multipart uploads, WebSocket/Realtime APIs and gRPC. These pass through unchanged.
  • TLS-pinning apps refuse the local CA. Use gateway mode for them.
  • SigV4-signed requests (Bedrock with IAM signing) are forwarded unmasked with a warning, because changing the body would break the signature. Bedrock API keys work.
  • Semantic drift. The model reasons about the persona: a Shenzhen company gets Shenzhen context. Pin persona.region if that matters.

FAQ

Does Shadow phone home?

No. It only forwards the requests you were already making, translated, to the providers you were already using. There is no telemetry and no account.

What if the model invents a value that looks like a fake?

Unmasking replaces exact fake strings only. Fakes are random, persona-specific and unique, so collisions with model output are rare. When one happens, the model sees a real value of yours put back in its place. The provider never learns it.

Can two tools share one identity?

Yes. Point them at the same data dir. Processes merge each other's vault entries before every save. To move an identity to another machine, copy persona.json, vault.bin and vault.key.

How do I see what was replaced?

RUST_LOG=info shadow run logs counts per request (never values). shadow scan shows findings. shadow vault export --i-understand dumps the mapping.

Does it slow things down?

Detection is a few regex passes plus an Aho-Corasick automaton, typically well under a millisecond per kilobyte. Streams are translated incrementally, so time to first token is unaffected apart from holding back at most one fake's length.

Is “Shadow” a model?

It can be. ml/ contains a small PyTorch token-classification model and a localhost sidecar. Enable [model_detector] to add learned entity detection. The Rust build never needs Python.

Bedrock, Azure, Vertex?

Azure OpenAI and Vertex hosts are intercepted by pattern, or you can add [proxy.routes]. Bedrock works with bearer API keys. SigV4-signed calls are passed through unmasked.
